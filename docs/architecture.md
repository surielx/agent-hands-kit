# アーキテクチャ

## 全体像

```
[クラウドAI] --(自分から出ていく接続: SSH/Tailscale, HTTPS)--> [ユーザーのWindows PC]
     ^                                                            |
     |                                                            +-- [Desktop Agent] 対話セッションで常駐し
     |                                                            |     GUIの見取りと操作を提供 (localhost:8791, トークン認証)
     |                                                            +-- [ローカルLLM] OpenCode経由で同一人物として応答
     +----(人間用入り口: Museアプリ/WebチャットへのGUI入力)---------+-- [コーディングAIアプリ] 同じくGUI/CLIで相談可能
     |
     +----(ファイル郵便ポスト: Drive共有フォルダの定期確認)----------> [成果物・指示ファイル]
```

要点は方向の非対称性への対処である。クラウドAIのVMには外から入る公開経路がないため、連携は常に次のどちらかになる。

- **クラウドAIが発信者になる**：SSH・HTTPS・ファイル取得など、AI側から接続を開始する。
- **人間用UIを経由する**：PC側のAI（またはクラウドAI自身がGUI操作で）が、チャットアプリの入力欄という「誰でも使える入り口」に書き込む。

## Desktop Agent の2層構造（なぜ分けるか）

Windowsでは SSH セッションはセッション0で動き、ログイン中ユーザーのデスクトップ（セッション1）が見えない。そこで：

- 常駐本体：スケジュールタスクで対話セッションに常駐するサーバー。`127.0.0.1` のみで待ち受け、`X-Token` ヘッダで認証。操作は単一ロックで直列化し、応答に実測時間と前面ウィンドウ情報を付ける。
- CLIクライアント：同じ exe のサブコマンド。SSH越しでも、PC上のAIのラッパースクリプト（`desktop.ps1`）からでも同じに叩ける。

### トークン節約のための snapshot 設計

- UI Automationツリーから「面白い要素」だけをボトムアップに刈り込む（名前なしの単なる Pane 等は落とす）。
- 要素IDはパス（種別＋AutomationId優先）から採る安定IDで、再snapshotでも同じ要素は同じIDを保つ。
- `--diff`（前回との差分）、`--region`（矩形で部分木に絞る）で、毎回全量を読まない。
- 応答に前面状態（`fg`）を常時添付し、状態確認の往復を減らす。

### 入力方式は2つを使い分ける

- プライマリ：クリップボード貼り付け。ただしクリップボードはWindowsセッション別なので、設定→読み戻し検証→Ctrl+V を本体側で完結させる（SSH側で設定しても対話側に届かない事故の対策）。
- セカンダリ：打鍵（SendInput）。貼り付けが許可されない入力欄があるため、両方式を常時選べるようにする。

### 待ち方は固定sleepでなく条件待ち

シーケンスの各ステップに `precond` / `expect`（プロセス名・ウィンドウ題名・UI要素テキストの部分一致＋タイムアウト）を付け、観測可能な状態を待って進む。失敗時は観測した前面状態付きで報告する。

## ファイル郵便ポスト

直接接続できない相手同士は、両者が到達できる共有フォルダを郵便ポストにする（詳細は `mailbox/README.md`）。

- 指示は前提を全部書いたタスクファイルとして置く（要約は前提を書き換えるので、原本を正とする）。
- 成果物と報告（REPORT）を同じ場所に返し、最終行マーカーで成否を機械判定する。
- 遅延はあるが、NAT・ファイアウォール・OS差をすべて回避できる最も堅い経路。

## 相談・委任ラッパー

- 相談ラッパー：対象AIのCLIを非対話で叩き、相談IDとセッションIDを保存して継続相談を可能にし、回答をファイルに残す。導入時は合言葉の往復ドリルで経路を実証する。
- 委任ハーネス：`patterns/delegation-harness.md` 参照。前提固定、足場の事前構築、生成→検証→報告の段階予算、報告フェーズの保証、汎用チェックのみ、が骨格。

## 既知の限界

- GUI操作は画面状態に依存する。ポップアップ、題名変更、ロック画面等で手順が崩れることがある。対策は「要所確認＋失敗時に確認」であり、完全な堅牢性ではない。
- PCがスリープ・電源オフの間は一切届かない。常駐連携にはPCの稼働が前提。
- 郵便ポスト方式は遅延が大きい（ポーリング間隔依存）。リアルタイム対話には向かない。
- 本キットの道具は強い権限（画面操作・キー入力）を持つ。`SECURITY.md` の前提を守ること。
